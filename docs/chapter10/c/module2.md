## 核心内容

### 一、延迟 vs 吞吐量

在 LLM 推理中，三个核心性能指标：

| 指标 | 全称 | 含义 |
|------|------|------|
| **TTFT** | Time To First Token | 用户发出请求到看到第一个 token 的时间（交互体验关键） |
| **延迟** | Latency | 首 token 生成后，后续 token 的输出速度 |
| **吞吐量** | Throughput | 系统单位时间内生成的总 token 数（系统效率评估） |

> 高吞吐量 ≠ 低延迟。吞吐量衡量系统整体效率，延迟关注单个用户体验。大批量推理时系统吞吐量很高，但个别请求可能因排队等待而延迟很长。

#### 批处理策略

增大 batch（批大小）可以提升吞吐量——权重矩阵只读一次，分摊到更多输入（"拼车效应"）。但 tradeoff 是：batch 越大，单请求延迟可能增加。

三种批处理方式：

| 方式 | 原理 | 优缺点 |
|------|------|--------|
| **静态批处理（Static Batching）** | 等凑够固定数量请求后一起处理 | 简单，但必须等最慢请求完成才能释放资源，GPU 利用率低 |
| **动态批处理（Dynamic Batching）** | 设定时间窗口，窗口内收到的请求打包 | 比静态灵活，但仍受"等最慢请求"问题困扰 |
| **持续批处理（Continuous Batching）** | 每个生成步骤（iteration）级别调度：完成的请求立即移出，新请求立即插入 | 最灵活，AnyScale 基准显示比静态批处理可达 **23x 吞吐提升**（来源：Orca, OSDI 2022） |

> 🌐 **补充（Web Search / Exa）**：微软的 **Sarathi-Serve**（OSDI 2024）提出 **Chunked Prefill**（分块预填充）——将 Prefill 请求切成等大小的 chunk，与 Decode 请求交错调度，避免长 Prefill 阻塞 Decode。Mistral-7B 在单卡 A100 上实现 2.6x 服务容量提升，Yi-34B 双卡上 3.7x。已集成进 vLLM。

> 🌐 **补充（Web Search / Tavily）**：2025 年论文 "Mind the Memory Gap"（arXiv 2503.08311）发现：大批量推理的吞吐量瓶颈不是算力，而是 **注意力机制 Decode 阶段的 DRAM 读取带宽饱和**。即使增大 batch，每个请求仍需读取自己的 KV Cache，超过"拐点"后吞吐量不再增长但延迟持续增加。

**权衡总结**：

| 目标 | 权衡点 |
|------|--------|
| 延迟 vs 吞吐量 | batch 越大 → 吞吐越高，但单请求延迟可能增加 |
| 效率 vs 精度 | KV Cache、量化等优化必须保持自回归因果性和语义准确性 |
| 显存 vs 性能 | KV Cache 随序列长度线性增长，限制最大 batch 或序列长度 |

### 二、提示词压缩

在自回归 LLM 中，用户输入的 prompt 并非"免费"——每个 prompt token 都要计算 K、V 并存入 KV Cache。过长 prompt 导致：① 显存占用大 ② 注意力计算量增加 ③ 冗余信息"稀释"注意力分配。

#### 硬提示词压缩

硬提示词压缩通过**缩短或简化自然语言 prompt 本身**来减少 token 数，输出仍然是可读文本。

![图10.6 硬提示词压缩](<../images/10.6.png>)

**图 10.6 解读**：从左到右展示了四种方法的演进：

| 方法 | 压缩方式 | 核心特点 |
|------|---------|---------|
| **Original** | 无压缩 | 基准，5 个 prompt 直接输入冻结 LLM |
| **SelectiveContext** | 冻结 LLM 做上下文筛选 | 用冻结模型的推理能力评估 token 相关性，5→3 |
| **LLMLingua** | 可训练 SLM（LoRA 微调）压缩 | 小模型学习压缩策略，5→2，压缩比更高 |
| **Nano-Capsulator** | 可训练 LLM（LoRA 微调）压缩 | 大模型压缩，更激进 |

两类具体方法：
- **选择关键内容**：基于句子/token 相关性筛选（用编码器匹配查询相关性），或训练 RL 控制器动态调整 prompt 长度
- **改写压缩**：将冗长 prompt 压缩为更短表述，保留核心语义

> 🌐 **补充（Web Search / Tavily）**：**LLMLingua**（微软，EMNLP 2023）使用小语言模型识别不重要的 token 并移除，实现 **最高 20x 压缩比**且性能损失极小（GSM8K 仅降 ~1.5 分）。后续 **LLMLingua-2**（NAACL 2025）将压缩建模为 token 分类任务，压缩速度比 LLMLingua 快 3-6x，且使用双向上下文（来源：arXiv 2403.12968）。

> 🌐 **补充（Web Search / Exa）**：有趣发现——对于**长上下文**，适度的压缩反而能**提升**性能（减少噪音），只在过高压缩比时才开始下降。对短上下文，压缩则始终有害（来源：ICLR 2025 Building Trust Workshop）。

#### 软提示词压缩

软提示词摆脱离散 token 依赖，通过**学习一组连续向量**替代自然语言 prompt。训练阶段这些向量作为可学习参数通过反向传播优化；推理阶段直接以 embedding 形式注入模型输入。

![图10.7 软提示词压缩](<../images/10.7.png>)

两类方法：
- **固定 LLM 参数的方法**：优化输入表示，不微调模型主体（如 Prompt Tuning、Prefix Tuning）
- **基于要点词元的方法**：将上下文转化为紧凑可复用的特殊 token，通常需要更新 LLM 参数（如 500xCompressor 将 500 个 token 压缩为 1 个特殊 token）

**软提示词的局限**：
- **推理开销**：软提示仍需参与前向传播和注意力计算，不自动降低推理计算
- **可解释性低**：连续向量不对应可读词语，每个维度的组合共同作用，不直观
- **泛化能力弱**：针对特定任务学习，对训练数据外的场景敏感

#### 视觉层面的 prompt 压缩

![图10.8 DeepSeek-OCR结构](<../images/10.8.png>)

将文本 prompt 转化为图像 → OCR/视觉编码提取信息 → 固定维度的图像表示减少 token 数。这是一种较实验性的方法。

> 从推理机制看：硬/软提示词都会扩展输入序列并参与自注意力计算。区别在于硬提示词由离散 token 经 embedding 映射，软提示词以学习好的连续向量直接注入。

### 三、状态空间模型（SSM）

![图10.9 空间状态模型](<../images/10.9.png>)

**图 10.9 解读**：SSM 可视为对传统 RNN 的扩展，在信号处理和长序列建模方面表现出色。与自回归 Transformer 依赖显式 KV Cache 不同，SSM 通过隐状态的连续更新以及训练阶段学习得到的权重矩阵实现对长期依赖信息的建模。

#### 从 RNN 到 SSM 到 Mamba 的演进

**RNN**（循环神经网络）：
```
h_t = f(W_hh · h_{t-1} + W_xh · x_t)
y_t = W_hy · h_t
```
隐藏状态在时间步之间传递。问题：① 计算无法并行（必须逐步） ② 梯度消失/爆炸导致长程依赖学习困难。

**SSM**（结构化状态空间模型）— 代表作 **S4**（Structured State Space for Sequence Modeling, ICLR 2022），首次通过对状态矩阵 A 施加结构约束（HiPPO 初始化 + 对角加低秩分解），使 SSM 在长序列任务上实用化，训练用卷积模式并行、推理转递归模式：
将离散序列映射到**连续时间动态系统**，通过一阶线性常微分方程定义状态转移：

$$h'(t) = Ah(t) + Bx(t), \quad y(t) = Ch(t) + Dx(t)$$

其中 A、B、C、D 是系统矩阵。离散化后可用**卷积模式并行训练**，推理时可转为递归模式。优点：并行训练效率高，长程依赖建模能力强。缺点：参数固定（A、B、C 不随输入变化），无法根据内容灵活响应。

**Mamba**（选择性状态空间模型）：

核心创新——**让系统矩阵 A、B、C 依赖于输入**（选择性机制，Selective Mechanism）。模型通过线性投影层从输入 $x(t)$ 动态生成 A、B、C：

```
标准 SSM：  A, B, C 是固定矩阵 → 对所有输入一视同仁
Mamba：    A(x), B(x), C(x) 由输入决定 → 根据内容选择性记住/遗忘
```

这让 Mamba 兼具 SSM 的**并行训练效率**和类似注意力机制的**内容感知能力**，推理时只需维护固定大小的隐藏状态，不需要 KV Cache。

> 💡 **类比**：RNN 是"流水线工人"按部就班但容易遗忘；SSM 是"物理模拟器"用固定规律高效但不够灵活；Mamba 是"智能过滤器"能根据输入实时调整策略。

#### SSM 的局限与最新进展

**局限**：
- 纯 SSM 在**精确检索任务**上仍弱于 Transformer（如 needle-in-a-haystack）。研究发现预训练 Mamba 模型仅达到同规模 Transformer **38% 的 ICL 性能提升**（来源：OpenReview）。
- 梯度消失问题在极长序列中仍可能发生。

> 🌐 **补充（Web Search / Exa + Tavily 交叉验证）**：2025-2026 年 SSM 领域的关键进展——
>
> **Mamba-3**（ICLR 2026 Oral，Together AI）：引入复值状态追踪和 MIMO（多输入多输出）变体，在 1.5B 规模上平均准确率比 Mamba-2 提升 1.8 个百分点，解码延迟与 Mamba-2 相当。
>
> **Bamba-9B**（IBM，2025.4）：混合 Mamba2 + Transformer 架构，用 3T token 训练达到 LLaMA-3.1-8B（5T token）的性能，推理吞吐量 **2.5x** 于同规模 Transformer。
>
> **Nemotron-H**（NVIDIA，2025.4）：替换 **92% 的注意力层**为 Mamba-2，56B 模型在 17 项任务中 16 项超过 Llama-3.1-70B，吞吐量 **2.4x** 于同规模 Transformer。
>
> **行业共识**：2025-2026 年的趋势是 **"Mamba + Transformer" 混合架构**，而非纯 SSM。IBM Granite 4.0 采用 9:1 的 Mamba-2/Transformer 比例，NVIDIA Nemotron-H 替换 92% 注意力层。

### 四、扩散语言模型（LLaDA 2.0）

![图10.10 扩散模型](<../images/10.10.png>)

**图 10.10 解读**：扩散模型的核心是两个过程——
- **前向加噪 $q(x_t | x_{t-1})$**：逐步向数据添加高斯噪声，直到变成纯噪声（已知过程）
- **反向去噪 $p_\theta(x_{t-1} | x_t)$**：学习从噪声恢复数据（模型需要学的）
- **离散化 $p_\theta(w | x_0)$**：将连续向量映射回离散词表

与自回归模型的关键区别：扩散模型可以在空间位置上**并行生成多个 token**，推理速度不受显存限制影响。但自然语言本质上是时间序列（有因果依赖），扩散模型在长文本生成中容易出现逻辑不一致。

#### 掩码去噪语言模型（MDLM）

MDLM 将文本生成视为**迭代去噪过程**：每次前向传播中部分 token 被随机掩码，模型根据未掩码的上下文恢复原始 token。

LLaDA 1.0（8B，NeurIPS 2025）证明了从零训练的 MDLM 可以与同规模 AR 模型媲美。但限制是推理速度慢（采样步数需等于生成长度）。

#### LLaDA 2.0：AR 到扩散的迁移学习

LLaDA 2.0 的核心创新是**不从头训练**，而是将预训练 AR 模型转换为扩散模型，有三个阶段：

![图10.11 LLaDA2.0训练过程](<../images/10.11.png>)

**图 10.11 解读**：训练过程采用 **Warmup-Stable-Decay（WSD）学习率调度**配合块大小 $L_B$ 的渐进调整：

**阶段 1：渐进式块大小预热（Warmup）**
- $L_B$ 从小到大逐步增加
- 训练初期接近自回归（$L_B$ 小），模型在严格因果约束下学习
- 随着 $L_B$ 增大，块内允许**双向注意力**（并行预测多 token），块间保持自回归顺序
- 平滑地从 AR 建模过渡到扩散风格

**阶段 2：稳定训练（Stable）**
- $L_B$ 固定为 4096（覆盖整个输入序列）
- 等效于经典 MDLM：块内全局注意力，完整建模上下文
- 在筛选后的大规模语料上广泛训练

**阶段 3：衰减阶段（Decay）**
- $L_B$ 从 4096 逐步缩小
- 从全局注意力过渡到局部注意力，降低显存消耗并加速推理
- 保留部分全局注意力以捕捉跨块关系

**后训练**：SFT + DPO（Direct Preference Optimization，直接偏好优化——使用"好的回答 vs 差的回答"的对比数据微调模型，使其输出更符合人类偏好）

#### 块扩散的核心机制

块扩散注意力掩码包含三种模式：

```
块扩散注意力掩码示意：
┌──────────────────────────┐
│  M_BC (块内)    │ ← 同一块内所有 token 互相可见（并行生成）
│  ████████████   │
├────────────────┤
│  M_OBC (块外)   │ ← 当前块可看到之前所有已生成的内容
│  ░░░░░░░░░░░░  │
├────────────────┤
│  M_BD (文档间)  │ ← 文档级全局注意力
│  ▒▒▒▒▒▒▒▒▒▒▒▒  │
└──────────────────┘
```

- **块内并行**（$M_{BC}$）：同一个 block 内所有 token 可互相看到，实现并行预测
- **块间串行**（$M_{OBC}$）：不同 block 之间保持自回归因果顺序
- **文档级**（$M_{BD}$）：限制在同一文档内，避免跨文档的虚假依赖

> 💡 **与 AR 的对比**：AR 每次生成 1 个 token（$L_B=1$），纯扩散模型一次性生成全部（$L_B=L$）。块扩散是两者之间的插值——$L_B$ 越大并行度越高但一致性风险越大。

#### LLaDA 2.0 成果

**LLaDA2.0-flash**（100B 参数，MoE 架构）：
- 平均得分 73.18，与 Qwen3-30B-A3B（73.60）不相上下
- 在**代码生成、工具使用、数学推理**等复杂任务中优于同类 AR 模型
- 通过 Confidence-Aware Parallel decoding 达到 **535 tokens/s**（来源：官方 GitHub）
- SGLang 集成支持 KV Cache 复用和块级并行解码

> 🌐 **补充（Web Search / Exa + Tavily 交叉验证）**：**LLaDA 2.1**（2026.2）引入 **Token Editing（token 编辑）**机制——生成后可以对个别不满意的 token 进行修改而不需要重新生成整个序列，这是 AR 模型**根本不具备**的能力。S-Mode 推理速度达到 **892 tokens/s**（代码生成），比 LLaDA 2.0 快 2x 以上（来源：arXiv 2602.08676）。
>
> 同时，Fast-dLLM v2（7B）仅用 ~1B token 微调就将 AR 模型转为块扩散模型，吞吐量达到 Qwen2.5-7B 的 **2.54x**（来源：arXiv 2509.26328）。

**A1**：

静态批处理，是等凑够固定数量的 batch 后再进行处理。需要等待固定数据接受完成，以块为调度粒度。
持续批处理，是有新的数据进来就插入进行处理，完成了直接移出。根据新来的数据进行调整。

**A2**：

硬提示词压缩通过缩短或者压缩自然语言本身进行压缩，因此在推理时将经过 LLM 的序列长度压缩来减少推理成本。局限是，硬提示词压缩依赖对内容核心内容进行提纯，压缩程度有限，并且压缩（selective word）直接影响到输出的 token 质量。
软提示词压缩通过学习一组特殊向量替代自然语言 prompt，在推理时控制特殊向量的序列长度来控制推理成本。将 token 压缩成特殊 token，可解释性差，压缩能力有限，泛化能力弱。

持续批处理（Continuous Batching，又称 iteration-level scheduling）相比静态批处理的核心优势在于**调度粒度从"整个序列"变为"单个生成步骤"**：

**静态批处理的问题**：
```
请求A: [T1, T2, T3] ← 3步就生成完了
请求B: [T1, T2, T3, T4, T5, T6, T7] ← 需要7步

静态批处理：必须等B也生成完才能释放A的位置
  Step 1-3: A和B都在处理 → GPU利用率高
  Step 4-7: A已完成但位置被占着 → GPU资源浪费
```

**持续批处理的解决**：
```
Step 3: A生成完毕 → 立即移出A → 插入新请求C
Step 4-7: B和C并行处理 → GPU始终满载
```

**为什么能同时提升吞吐和降低延迟**：
- **吞吐量提升**：GPU 始终有活干，不会因为等最慢请求而空转。AnyScale 基准显示可达 23x 吞吐提升
- **延迟降低**：新请求不需要等整个 batch 处理完，可以在任何生成步骤被插入，减少了排队等待时间

**关键 insight**：持续批处理本质是把 GPU 调度从"批处理级别"（秒级）变为"token 级别"（毫秒级），让资源的分配粒度与实际需求匹配。

</details>

**Q2 批改**：对硬/软压缩的机制和局限理解正确。硬压缩减少 token 数 → 减少 KV Cache 和注意力计算量；软压缩用更短的向量序列替代原始 prompt。但有一个关键区别没有提到：**硬压缩减少的是实际的序列长度（token 数变少），软压缩减少的是每个 token 的"信息密度"（用更少的特殊 token 承载更多信息），但序列长度不一定变短**。这也是为什么软压缩"不自动降低推理计算"——向量仍然参与完整的注意力计算。 — 得分：**7/10**

<details>
<summary>📖 Q2 参考答案</summary>

| | 硬提示词压缩 | 软提示词压缩 |
|---|---|---|
| **减少成本的机制** | 直接减少 token 数量 → KV Cache 变小、注意力矩阵变小、FLOPs 减少 | 用更短的特殊 token 序列替代原始 prompt → 序列物理长度缩短 |
| **推理时的实际效果** | 输入序列真正变短，计算量和显存确实减少 | 特殊 token 仍需参与完整前向传播和注意力计算，计算量不一定减少 |
| **局限** | 压缩程度有限（过度压缩会丢失关键信息）；压缩质量依赖选词算法 | 可解释性差（连续向量不对应可读词语）；泛化能力弱（针对特定任务学习）；推理开销不一定降低 |
| **代表方法** | LLMLingua（20x 压缩）、SelectiveContext | Prompt Tuning、500xCompressor |
| **输出** | 可读的自然语言 | 不可读的连续向量 |

**关键区分**：硬压缩是"删掉不重要的词"，序列真的变短了；软压缩是"用几个特殊向量浓缩信息"，虽然特殊 token 数量少但每个 token 承载的信息更密集，且仍需参与注意力计算。所以软压缩的主要优势不在于推理加速，而在于**参数高效的任务适配**（不用微调整个模型就能让模型适应新任务）。

</details>

**Q3 批改**：三个阶段 $L_B$ 变化的目的理解正确。特别值得肯定的是你诚实地指出了"文档中对 $L_B$ 没有作详尽的背景介绍"——这是文档的不足。关于"为什么不全程保持 $L_B$ 为最大值"的回答不够完整：全程大 $L_B$ 的问题是①训练不稳定（模型从纯 AR 直接跳到大块并行去噪，优化困难）②显存爆炸（块内所有 token 的 KV 都要缓存）③推理时不实用（实际部署需要较小的块大小以平衡速度和质量）。 — 得分：**6/10**

<details>
<summary>📖 Q3 参考答案</summary>

$L_B$ 是 **Block Size（块大小）**——每次并行处理的连续 token 数量。$L_B=1$ 等价于纯 AR（逐 token 生成），$L_B=L$（序列总长度）等价于纯扩散模型（一次性生成全部）。

**三阶段的设计目的**：

**阶段 1（Warmup，$L_B$ 从小到大）**：
- **为什么不直接用大 $L_B$**：预训练 AR 模型的权重是为逐 token 预测优化的。如果直接用大 $L_B$（如 4096），模型需要一步学会"同时预测 4096 个 token 并保持一致性"——这对优化器来说太难了，训练会不稳定甚至崩溃
- **渐进增大的好处**：$L_B$ 从 1 开始，模型先在熟悉的 AR 模式下工作，然后逐步适应更大的并行预测范围，平滑过渡

**阶段 2（Stable，$L_B$ 固定为 4096）**：
- 模型已经适应了大块并行去噪，此时在最大块大小上充分训练
- 等效于经典 MDLM：块内全局双向注意力，最大程度利用扩散模型的并行优势

**阶段 3（Decay，$L_B$ 从大缩小）**：
- **为什么不保持最大值**：实际部署时需要平衡推理效率和生成质量。$L_B=4096$ 意味着每次要同时生成 4096 个 token，显存占用巨大且出错后无法局部修正
- 缩小 $L_B$ 让模型学会在较小的块上高效工作，推理时速度更快、显存更低
- 仍保留部分全局注意力以避免完全丢失长程依赖

**类比**：就像学游泳——先在浅水区适应（Warmup），然后到深水区训练耐力（Stable），最后回到中等深度练习实用技巧（Decay）。全程在深水区反而学不好。

</details>
