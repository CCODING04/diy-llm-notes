## 核心内容

### 1. 智能体基准：从"回答问题"到"完成任务"

知识类基准测的是"知不知道"，指令遵循基准测的是"听不听话"。智能体基准再升一级——测的是模型能否在**复杂环境中通过工具调用和迭代规划独立完成任务**。

核心区别：

```
知识/指令基准：
  输入 prompt → 模型输出文本 → 与参考答案比较

智能体基准：
  输入任务描述 → 模型使用工具 → 观察环境反馈 → 调整策略 → 再次行动
  → ...循环... → 最终结果被环境自动验证
```

#### 1.1 SWE-Bench：自动修 Bug 并提交 PR

**任务**：给定一个 GitHub issue（如"Django 的某个查询在特定条件下返回错误结果"），模型需要在代码库中定位问题、修改代码、并通过单元测试。

![SWEBench评测流程](<../images/12-26-SWEBench评测流程示意图.png>)

**数据**：来自 12 个真实 Python 开源项目（django/django 850 个、sympy/sympy 386 个、scikit-learn 229 个等），共 2294 个任务。评估方式为直接运行单元测试验证修复是否成功。

**SWE-Bench Verified**：原始 SWE-Bench 中存在部分问题描述不准确或测试用例有误。Verified 子集通过人工重新验证和修正，包含 500 个高质量任务，目前是代码智能体能力的**事实标准基准**。

**关键数据**（截至 2026 年 6 月）：

| 模型 | SWE-Bench Verified |
|------|-------------------|
| Claude Mythos Preview | 93.9% |
| Claude Opus 4.8 | 88.6% |
| GPT-5.5 | 82.6% |
| Gemini 3.1 Pro | 79.8% |

**数据污染问题**：OpenAI 的审计发现，所有前沿模型都与 SWE-Bench 存在训练数据重叠——59.4% 的高难度任务的测试用例存在缺陷。OpenAI 已停止报告 Verified 分数，转而使用新的更严格的 SWE-Bench Pro。

> 🌐 **补充（Web Search / OpenAI Audit）**：SWE-Bench 的污染困境是评估危机（模块 1）在代码领域的典型表现——当一个基准变得"重要到必须报告"，模型的训练数据就开始包含它。解决方案不是放弃基准，而是持续更新（SWE-Bench Pro → 新一轮评估 → …可能再次被污染）。

#### 1.2 CyBench：网络安全夺旗挑战

**任务**：完成 40 个网络安全领域的 Capture The Flag（CTF）挑战——逆向工程、漏洞利用、密码学破解等。

![CyBench评测流程](<../images/12-27-CyBench评测流程示意图.png>)

**独特设计**：任务难度通过**人类首次解决时间**来度量——有些挑战对人类专家也极具挑战性（耗时可达 24 小时）。这使得 CyBench 不仅测量"模型能不能做"，还测量"和人类专家比起来有多快/多好"。

![CyBench排行榜](<../images/12-28-不同模型在CyBench的排行榜.png>)

**核心能力要求**：CyBench 超越了纯代码能力，要求模型具备安全领域的专业知识——理解二进制文件结构、识别漏洞模式、编写 exploit 代码。这比 SWE-Bench（"读懂代码 + 修 Bug"）在领域专业性上更进一步。

#### 1.3 MLEBench：自动化机器学习竞赛

**任务**：自动参与 75 个 Kaggle 机器学习竞赛——数据处理、模型选择与训练、超参调优、结果提交，全流程自主完成。

![MLEBench评测流程](<../images/12-29-MLEBench评测流程示意图.png>)

**当前水平**：最佳模型获得任何奖牌（铜牌及以上）的准确率也**低于 20%**。

![MLEBench排行榜](<../images/12-30-MLEBench.png>)

**为什么这么难？** MLEBench 是三类智能体基准中最困难的，因为它要求的能力栈最宽：

```
SWE-Bench 需要的：   读代码 + 定位 Bug + 写补丁 + 通过测试
CyBench 需要的：     + 安全领域知识（漏洞/加密/逆向）
MLEBench 需要的：    + 数据理解 + 特征工程 + 模型选型
                     + 超参调优 + 实验设计 + 防止过拟合
```

MLEBench 的低成功率（< 20%）表明：**当前的 LLM 在"端到端的自主研究"方面仍有巨大差距**。它们会写代码、会调参，但无法像人类数据科学家一样在"试错→观察→调整策略"的循环中做出高质量的元决策。

### 2. 智能体基准的核心局限

**局限一：评估的是"系统"而非"模型"**

SWE-Bench 的分数依赖于 agent scaffolding（提示策略、工具设计、搜索算法）——同一个基础模型配上不同的 agent 框架，得分可能相差 20%+。这是模块 1 中"评估系统 vs 评估方法"范式的具体表现——SWE-Bench 上的高分可能来自更好的 agent 架构，而非更好的基座模型。

**局限二：环境简化**

SWE-Bench 的代码库是固定的、可本地运行的——真实软件工程的复杂性（遗留代码、无文档的依赖、分布式系统交互）远未被覆盖。

**局限三：分数不反映安全风险**

CyBench 中模型学会的漏洞利用技能（写出有效的 exploit）——在基准上是高分，在现实世界是安全威胁。能力评估和风险评估在此交织。

### 3. 纯推理基准：ARC-AGI

#### 3.1 哲学：剥离一切知识，只测推理

ARC-AGI 的核心理念是：**如果我想测"智能"本身，我必须先消除知识的干扰**。

```
MMLU/HLE：    "你知道什么？"       ← 知识和推理交织
ARC-AGI：     "你能想出规则吗？"   ← 纯推理，零知识要求
```

#### 3.2 设计：视觉网格变换

ARC-AGI 提供一系列视觉化的输入-输出网格对（彩色方块阵列），模型需要推断出变换规则并应用于新的输入。整个过程**不涉及任何语言**。

![ARC-AGI-1评测示意图](<../images/12-31-ARC-AGI-1评测示意图.png>)

**为什么传统 LLM 表现极差？** 因为 LLM 的训练数据中充满了文本模式的统计规律——ARC-AGI 的网格变换没有文本描述、没有领域知识可调用、没有任何"常见搭配"可统计依赖。它测的是真正的抽象推理——看到三个例子后猜出第四个的规律。

**ARC-AGI-1 得分**（2025 年初）：
- 普通人类：~80%
- o3（高推理模式）：87.5%
- GPT-4o：~10%

![ARC-AGI-1得分](<../images/12-32-不同模型在ARC-AGI-1的得分.png>)

#### 3.3 ARC-AGI-2：更难的抽象推理

ARC-AGI-1 被 o3 高效解决后，ARC-AGI-2 发布——难度大幅提升：

![ARC-AGI-2评测示意图](<../images/12-33-ARC-AGI-2评测示意图.png>)

**当前得分**（截至 2026 年 6 月）：
- Gemini 3.1 Pro：77.1%
- Claude Opus 4.6：68.8%
- 人类：仍在 90%+

#### 3.4 ARC-AGI-3：下一代

> 🌐 **补充（Web Search）**：ARC-AGI-3 于 2026 年初发布，形式为回合制游戏环境——无规则说明、无指令。前沿 LLM 得分低于 **1%**，而简单的 CNN 方法反而达到 **12.58%**。这暗示当前 Transformer 架构在纯模式识别方面的先天劣势——纯粹在文本 token 上训练的模型，当被要求进行完全脱离语言的抽象模式推理时，其能力远不如专门为视觉模式识别设计的轻量架构。

**这意味着什么？** ARC-AGI 系列的结果在挑战模块 1 中 Karpathy 的"锯齿状智能"论断——LLM 在可验证的符号推理（数学、代码）上达到超人类水平，但在纯粹的抽象模式识别上可能不如一个几十年前的 CNN。这不是"智力高低"的问题，而是**智能形态根本不同**的问题。

### 4. 模块小结：三种基准的难度光谱

```
知识类（MMLU→HLE）    ：模型已接近/超过人类天花板
指令遵循（Arena→WildBench）：自动化评估质量在接近人类判断
智能体（SWE→MLE）     ：代码任务快速进步，端到端研究仍有巨大差距
纯推理（ARC-AGI）      ：暴露了 LLM 智能形态的根本局限
```

这四条线索指向同一个结论，呼应模块 1 的 Karpathy 判断：**我们可能永远无法用单一分数回答"模型到底有多好"**——因为在不同类型的任务上，LLM 的能力分布是锯齿状的，有些尖刺已经远超人类，有些深谷甚至不如简单 CNN。

### 📝 批改结果

**Q1 批改**：20% 差距来自 agent scaffolding 的判断正确。你给出的实践建议——"找到适合 agent 框架的基座模型以获得系统整体最优"——在工程层面也是合理的优化思路。

但题目想引导的更深一层是**方法论层面的批判**：这 20% 的差距意味着 SWE-Bench 分数无法被归因——你无法区分"高分是来自更强的基座模型还是来自更聪明的 agent 脚手架"。如果一个排行榜将所有模型-框架组合放在一起比较，它实际上是在比较"谁的工程团队更擅长设计 agent 提示策略"，而非"谁的基座模型更强"。这就是模块 1 中"评估系统 vs 评估方法"范式的具体回响——SWE-Bench 在设计上是系统评估，但如果有人试图用它来做模型选型（方法评估），就会因为无法控制 scaffolding 变量而得出误导性结论。正确的做法是：**固定 scaffolding，只换基座模型，做受控对比**，才能归因性能差异。 — 得分：**6/10**

<summary>📖 Q1 参考答案</summary>

**20% 差距说明了什么？**

它证明 SWE-Bench 分数中至少 20% 的方差来自非模型因素——提示策略设计、代码搜索算法、测试结果解析逻辑等。同一个基座模型可以"看起来"相差 20%，仅仅因为提示方式不同。

**对"用 SWE-Bench 选基座模型"的启示**：

SWE-Bench 在设计上是一个**系统级评估**——它比较的是"基座模型 + agent scaffolding"的完整产物。用它来选择基座模型存在一个根本的方法论缺陷：**无法归因**。

正确的做法：
1. 如果你想选基座模型 → 固定同一套 agent scaffolding，只换模型做受控对比
2. 如果你想选 agent 框架 → 固定同一个基座模型，只换 scaffolding
3. 公开排行榜上的 SWE-Bench 分数 → 只能告诉你"谁的系统整体最强"，不能告诉你"为什么强"

这与模块 1 的评估框架直接呼应——在"环节二：如何调用模型？"中，工具使用和 agent 框架的选择会根本性地影响评估结论。

| 层次 | SWE-Bench 需求 | MLEBench 需求 |

**Q3 批改**：你准确把握了核心矛盾——文本表征和视觉推理之间存在 gap，LLM 的能力受限于其训练模态。更进一步，你指出了一个重要的研究方向（视觉-文本表征对齐），这说明你在从"观察现象"延伸到"思考解决方案"。

两个可深化的角度：① **CNN 凭什么赢**——不只是"LLM 不擅长"，而是 CNN 的**架构本身就是空间关系的天然编码器**。3×3 卷积核在数学上就是"检测相邻像素的关系"，池化层就是"检测平移不变性"。CNN 不需要"学会"空间推理——它的归纳偏置（inductive bias）就是为空间模式匹配而生的。而 LLM 必须从 token 序列中**学**空间关系——"第1行第3列"和"第1行第4列"在文本序列中可能相隔数十个 token，空间邻接性被完全破坏；② **对 AGI 的更深层含义**——不是"LLM 不够强所以不是 AGI"，而是**AGI 可能需要异构架构**。不同类型的问题需要不同的计算基质（空间推理→CNN、符号推理→Transformer、因果推理→?），单一架构可能永远无法在所有维度上同时达到人类水平。这挑战了"Scale is all you need"的假设。 — 得分：**7/10**

<details>
<summary>📖 Q3 参考答案</summary>

**为什么 CNN > LLM？架构级原因**

CNN 的归纳偏置（inductive bias）天然匹配 ARC-AGI 的任务本质：
- **卷积核** = 局部空间关系检测器（"相邻的像素是什么颜色？"）——不需要学，这是架构自带的
- **平移等变性** = 同样的模式出现在不同位置，CNN 自动识别——不需要学，这是架构自带的
- **池化** = 对小的空间位移不敏感——不需要学，这是架构自带的

ARC-AGI 的"规则"正是这些空间变换——平移、旋转、填充、相邻。CNN 的**架构本身已经内置了这些操作的计算基础**。

而 LLM 必须把网格展平成 token 序列——"第3行第4列是红色"——空间上相邻的两个像素在 token 序列中可能隔了几十个 token，模型必须从零学习"这些远距离 token 之间其实是空间邻居"。归纳偏置完全不匹配。

**对"AGI 还有多远"的意义**

这个结果不是告诉你"LLM 太弱了"，而是告诉你**单一架构假设可能是错的**。人类大脑也不是一个单一的通用处理器——视觉皮层（V1/V2/V4）和语言皮层（Broca/Wernicke）使用不同的神经结构和计算原理。ARC-AGI 的结果暗示：AGI 可能需要**异构架构的集成**，而非在一种架构上无限 scale。不同类型的智能——空间推理、符号推理、因果推理——可能需要不同的计算基质。

</details>
