## 核心内容

### 一、内存合并（Memory Coalescing）：让数据搬运更整齐

在讨论 Tiling 之前，需要先理解 GPU 内存访问的一个底层优化——**内存合并**。这是硬件层面的优化，决定了"同样搬运 32 个数，为什么有时只需 1 次内存事务，有时需要 32 次"。

#### 1.1 DRAM 的突发模式（Burst Mode）

GPU 的全局内存（HBM/DRAM）有一个关键硬件特性：**读取一个地址时，实际返回的是包含该地址的一整块连续数据**。

```
假设突发段大小 = 4 字（16 字节）

地址:  [0] [1] [2] [3] | [4] [5] [6] [7] | ...
突发段:  ← 段 0 →       ← 段 1 →

当你读取地址 0 时：
  实际返回：[0] [1] [2] [3] 一整段
  不是只返回 [0] 这一个值

为什么这么设计？
  DRAM 访问最耗时的步骤是"定位行地址 + 传输数据到放大器"
  一旦这个步骤完成，同一行的相邻数据可以"免费"连续读出
  → 突发模式利用了这个特性，一次访问获取一整块数据
```

#### 1.2 内存合并的原理

Warp（32 个线程）同时访问全局内存。如果这些访问地址是**连续的**，硬件可以将 32 次独立访问**合并为少量内存事务**。

```
情况 1：合并访问（Coalesced）✅

  线程 0 读地址 0
  线程 1 读地址 1
  线程 2 读地址 2
  ...
  线程 31 读地址 31

  这 32 个地址连续 → 硬件合并为 8 次突发读取（32/4=8）
  → 吞吐量 = 4× 提升

情况 2：非合并访问（Uncoalesced）❌

  线程 0 读地址 0
  线程 1 读地址 100
  线程 2 读地址 200
  ...
  线程 31 读地址 3100

  地址分散在不同突发段 → 每次访问都是独立的内存事务
  → 需要 32 次独立读取 → 吞吐量极低
```

#### 1.3 矩阵乘法中的内存合并

以矩阵乘法为例，矩阵在内存中按 row-major（行优先）存储：

```
矩阵 A（2×4）在内存中的布局：
  A[0,0] A[0,1] A[0,2] A[0,3] A[1,0] A[1,1] A[1,2] A[1,3]
  ← 第 0 行连续 →       ← 第 1 行连续 →

按列遍历（❌ 不合并）：
  线程 0 读 A[0,0]（地址 0）
  线程 1 读 A[1,0]（地址 4）← 跨越了一整行！
  → 地址不连续 → 无法合并 → 性能差

按行遍历（✅ 合并）：
  线程 0 读 A[0,0]（地址 0）
  线程 1 读 A[0,1]（地址 1）← 紧挨着
  线程 2 读 A[0,2]（地址 2）
  ...
  → 地址连续 → 硬件合并为 1 次突发读取 → 性能好
```

> 💡 **关键规则**：在 GPU 编程中，让同一个 Warp 内的线程访问**连续的内存地址**。这个看似简单的原则，却是所有后续优化（Tiling、FlashAttention）的基础。

### 二、Tiling（分块）：让数据在片上多用几次

#### 2.1 问题：朴素矩阵乘法的内存灾难

考虑两个 N×N 矩阵相乘：C = A × B

```
朴素算法：

for i in range(N):
    for j in range(N):
        C[i][j] = 0
        for k in range(N):
            C[i][j] += A[i][k] * B[k][j]   ← 每次都从 HBM 读取！

问题 1：重复读取
  A[i,k] 被第 i 行的所有线程重复读取 N 次
  B[k,j] 被第 j 列的所有线程重复读取 N 次
  → 每个元素从 HBM 读取 N 次！

问题 2：非合并访问
  A 按行读取 → 合并 ✅
  B 按列读取 → 非合并 ❌（row-major 存储）
  → B 的访问效率极低
```

#### 2.2 Tiling 的核心思想

```
核心思想：把大矩阵切分成小块（Tile），一次性搬到共享内存，
         在共享内存中完成所有能做的计算，然后再搬下一块。

类比：
  你要从仓库（HBM）取 100 本书计算总价
  笨办法：每次从仓库取 1 本，算完放回去，再取下一本 → 跑 100 趟
  Tiling：一次从仓库取 10 本书到工作台（共享内存），
         在工作台上算完这 10 本，再回去取下一批 → 只跑 10 趟
```

具体做法（2×2 分块示例）：

```
原始矩阵 A（4×4）和 B（4×4），分块大小 T=2

  A 矩阵:                B 矩阵:
  ┌─────┬─────┐         ┌─────┬─────┐
  │ A00 │ A01 │         │ B00 │ B01 │
  │ 2×2 │ 2×2 │         │ 2×2 │ 2×2 │
  ├─────┼─────┤         ├─────┼─────┤
  │ A10 │ A11 │         │ B10 │ B11 │
  │ 2×2 │ 2×2 │         │ 2×2 │ 2×2 │
  └─────┴─────┘         └─────┴─────┘

计算 C[0,0] = A00×B00 + A01×B10：

步骤 1: 加载 A00 和 B00 到共享内存
         在共享内存中计算 A00×B00（部分和）

步骤 2: 加载 A01 和 B10 到共享内存
         在共享内存中计算 A01×B10（部分和）

步骤 3: 累加到 C[0,0]

关键：同一块数据在共享内存中被复用多次！
  A00 被加载 1 次，但在共享内存中被 4 个线程同时使用
  对比朴素算法：A00 被从 HBM 读取 2 次
```

#### 2.3 Tiling 的数学分析

```
朴素算法（无 Tiling）：
  每个输入元素从 HBM 读取 N 次
  总 HBM 读取量：2 × N² × N = 2N³

Tiling 算法（块大小 T）：
  每个元素从 HBM 读取 N/T 次（只加载它所在的块）
  每个元素从共享内存读取 T 次（块内复用）
  总 HBM 读取量：2 × N² × (N/T) = 2N³/T

  HBM 读取量减少为原来的 1/T！

具体数值：
  N = 4096, T = 128
  朴素：2 × 4096³ ≈ 1374 亿次 HBM 读取
  Tiling：2 × 4096³ / 128 ≈ 10.7 亿次 HBM 读取
  减少 128 倍！
```

从屋顶线模型理解 Tiling：

```
操作强度 = FLOPs / Bytes

朴素矩阵乘法：
  FLOPs = 2N³（乘加运算）
  Bytes = 2N³（每个元素从 HBM 读 N 次）
  操作强度 = 2N³ / 2N³ = 1 FLOP/Byte  ← 极低！内存受限

Tiling 矩阵乘法：
  FLOPs = 2N³（不变）
  Bytes = 2N³/T（HBM 读取减少 T 倍）
  操作强度 = 2N³ / (2N³/T) = T FLOPs/Byte  ← 提升 T 倍！

T = 128 时：操作强度从 1 提升到 128 → 从内存受限推向计算受限
```

#### 2.4 Tiling 的工程复杂性

Tiling 在实际工程中远比"切块就行"复杂，涉及多个约束的平衡：

**约束 1：块大小与共享内存容量**

```
块大小 T 决定需要多少共享内存：
  每个块需要存储：T×T 的 A 子矩阵 + T×T 的 B 子矩阵
  共享容量 = 2 × T² × sizeof(float) = 2 × T² × 4 字节

A100 共享内存 = 192KB：
  T = 64  → 2 × 64² × 4 = 32KB  ✅ 充裕
  T = 256 → 2 × 256² × 4 = 512KB ❌ 超出！

→ T 不能太大，受限于共享内存容量
```

**约束 2：块大小与突发传输段的对齐**

```
如果矩阵尺寸不是块大小的整数倍，会产生填充问题：

矩阵列 = 257, 块大小 = 128
  → 需要 ceil(257/128) = 3 个块
  → 第 3 个块只包含 1 列有效数据，其余 127 列是空的
  → 对应的 SM 几乎空转 → 利用率极低

更严重的是突发传输段对齐：
  第 1 行：完美对齐，1 次突发读取
  第 2 行：因为多了一个元素，跨越两个突发段
  → 需要 2 次读取 → 内存访问量翻倍！

解决方法：Padding（填充）使矩阵尺寸变成规整值
  257 列 → 填充到 256 或 512
```

**约束 3：与内存合并的兼容**

```
Tiling 必须同时满足：
  ① 块内数据在共享内存中复用 → 减少 HBM 访问
  ② 加载块时的 HBM 访问是合并的 → 高带宽利用率

如果块的加载顺序导致非合并访问，
则 Tiling 节省的带宽可能被低效的加载抵消！
```

> 💡 **补充（课程资料）**：这是 GPU 矩阵乘法性能表现"令人困惑的根源之一"。看似简单的分块操作，实际上需要同时权衡：共享内存容量限制、突发传输段对齐、SM 负载均衡、内存合并访问等多个约束。任何一个没处理好，都可能导致性能断崖式下降。

### 三、重计算（Recomputation）：用计算换内存

#### 3.1 问题：前向传播的激活值占大量显存

训练神经网络时，**前向传播产生的中间激活值**需要在反向传播中使用，必须保存下来。

```
3 个 Sigmoid 层堆叠：

  x → Sigmoid(x) → S1 → Sigmoid(S1) → S2 → Sigmoid(S2) → out

前向传播需要存储：
  x（输入）、S1、S2、out

反向传播需要：
  读取 S1、S2、x、out → 计算梯度

内存操作：
  前向：1 次读 x，3 次写（S1、S2、out）
  反向：4 次读（S1、S2、x、out），1 次写 dx
  总计：8 次 HBM 访问
```

对于大模型（如 LLM），激活值占用的显存非常惊人：

```
GPT-3 175B，batch=1, seq_len=2048：
  每层激活值 ≈ batch × seq × hidden × 4 bytes
  = 1 × 2048 × 12288 × 4 ≈ 100 MB/层
  96 层 × 100 MB ≈ 9.6 GB（仅激活值！）

加上梯度和优化器状态：
  总显存需求远超单卡 80GB
```

#### 3.2 重计算的核心思想

```
核心思想：不存储中间激活值，反向传播时重新计算

前向传播（不存 S1、S2）：
  x → Sigmoid → S1 → Sigmoid → S2 → Sigmoid → out
  只存储：x 和 out
  不存储：S1、S2

  内存操作：1 次读 x，1 次写 out

反向传播（重新计算 S1、S2）：
  读取 x 和 out → 在 SM 本地内存中重新计算 S1 = Sigmoid(x)
  → 在 SM 本地内存中重新计算 S2 = Sigmoid(S1)
  → 用计算出的 S1、S2 计算梯度

  内存操作：2 次读（x、out），1 次写 dx

总计：5 次 HBM 访问（对比朴素的 8 次，减少 37.5%）
```

#### 3.3 为什么重计算是划算的

```
关键前提：计算单元有大量闲置时间（内存受限状态）

朴素方案：
  计算: 10μs | 等数据: 50μs → 利用率 17%
  → 计算单元 83% 的时间在空等

重计算方案：
  计算: 20μs（多了一倍，因为要重算）
  等数据: 20μs（减少了，因为 HBM 访问少了）
  → 利用率 50%

  → 用"过剩的计算能力"换"紧缺的内存带宽"
  → 计算变慢了，但总时间可能反而更快
  → 而且显存占用大幅减少，可以放更大 batch
```

#### 3.4 PyTorch 中的实现

```python
import torch.utils.checkpoint as checkpoint

class MyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList([TransformerBlock() for _ in range(96)])

    def forward(self, x):
        for layer in self.layers:
            # checkpoint 包裹：前向不存激活值，反向时重新计算
            x = checkpoint.checkpoint(layer, x, use_reentrant=False)
        return x

# 激活值内存：
#   无 checkpoint: O(L) = 96 层 × 每层激活值
#   有 checkpoint: O(√L) ≈ 10 层的激活值
#   → 节省约 90% 的激活值显存
```

#### 3.5 重计算的适用条件

```
✅ 适合重计算的场景：
  - 计算受限程度低（内存受限，计算单元有闲置）
  - 计算成本相对较低（如 Sigmoid、ReLU、LayerNorm）
  - 激活值占用大量显存（深层网络、大序列）

❌ 不适合重计算的场景：
  - 计算已经饱和（计算受限区，重算会增加总时间）
  - 计算成本很高（如某些复杂的注意力计算，重算代价大）
  - 内存不是瓶颈（显存充裕）
```

### 四、三种技术的统一视角

将内存合并、Tiling、重计算放在屋顶线模型中统一理解：

```
共同目标：提高操作强度（FLOPs/Byte），从内存受限区推向计算受限区

                操作强度
内存合并:        ×1 → ×4    （合并访问，同样带宽传更多数据）
Tiling:          ×1 → ×T    （数据在片上复用，HBM 访问减少 T 倍）
重计算:          ×1 → ×1.6  （HBM 访问减少，但 FLOPs 增加）
三者组合:        ×1 → ×4T+  （叠加效果）

┌─────────────────────────────────────────────┐
│  屋顶线模型                                    │
│                                               │
│         ╱╲  计算天花板                         │
│        ╱  ╲                                   │
│       ╱    ╲ ← 无优化：在左侧很远              │
│      ╱      ╲                                 │
│     ╱        ╲                                │
│    ╱          ╲                               │
│   ╱   内存合并  ╲ ← 向右推移                   │
│  ╱    + Tiling  ╲                             │
│ ╱     + 重计算    ╲ ← 更接近计算受限区          │
│╱──────────────────╲                           │
└──────────────────────────────────────────────→ 操作强度
```

三者的互补关系：

| 技术 | 优化层面 | 减少的是 | 代价 |
|------|---------|---------|------|
| 内存合并 | 硬件 | 同一突发段内的冗余内存事务 | 需要按连续地址访问 |
| Tiling | 算法 | 跨块的 HBM 重复读取 | 需要共享内存 + 分块逻辑 |
| 重计算 | 策略 | 激活值的 HBM 存储 | 增加计算量 |

三者**不是替代关系，而是叠加关系**。实际的高性能实现（如 FlashAttention）同时使用了这三种技术。

<details>
<summary>📖 Q2 参考答案</summary>

**Tiling 减少 HBM 访问量的原理**：

把大矩阵切分成 T×T 的小块，一次性从 HBM 加载到共享内存，在共享内存中完成该块相关的所有计算，然后再加载下一块。核心是**数据在共享内存中被复用**，避免从 HBM 重复读取。

**朴素矩阵乘法的 HBM 读取量**：

每个 C[i][j] 需要 N 次乘加，每次乘加读 A 和 B 各 1 个。C 有 N² 个元素。
总 HBM 读取 = N² × N × 2 = 2N³

**Tiling 矩阵乘法的 HBM 读取量**：

块运算总次数 = (N/T)³（输出块数量 × (N/T)³/(N/T)² = (N/T) 次沿 k 维累加）。
每次块运算加载 2 个 T×T 块 = 2T² 个元素。
总 HBM 读取 = (N/T)³ × 2T² = 2N³/T

**N=4096, T=128 时**：

朴素：2 × 4096³ ≈ 1374 亿次 HBM 读取
Tiling：2 × 4096³ / 128 ≈ 10.7 亿次
减少 128 倍（等于块大小 T）。

**从屋顶线模型理解**：FLOPs 不变（2N³），Bytes 减少 T 倍（2N³/T）→ 操作强度从 1 FLOP/Byte 提升到 T FLOPs/Byte → 从内存受限推向计算受限。

</details>

<summary>📖 Q3 参考答案</summary>

**为什么重计算划算**：关键前提是 GPU 处于内存受限状态——计算单元有大量闲置时间。

```
朴素方案：
  计算: 10μs | 等数据: 50μs → 利用率 17%
  → 计算单元 83% 时间在空等

重计算方案：
  计算: 20μs（翻倍，要重算激活值）
  等数据: 20μs（减少了，HBM 访问从 8 次降到 5 次）
  → 利用率 50%
  → 用"过剩的计算能力"换"紧缺的内存带宽"
```

以 3 个 Sigmoid 堆叠为例：
- 朴素：HBM 8 次（前向 4 次 + 反向 4 次）
- 重计算：HBM 5 次（前向 2 次 + 反向 3 次），减少 37.5%
- 激活值显存从 O(L) 降为 O(√L)，L 为层数

**适用条件**：
- ✅ 内存受限（计算单元有闲置）
- ✅ 激活值占用大量显存（深层网络、大序列）
- ✅ 重算成本低（Sigmoid、LayerNorm 等轻量操作）
- ❌ 计算已饱和（计算受限区，重算增加总时间）
- ❌ 内存不是瓶颈（显存充裕）

PyTorch 实现：`torch.utils.checkpoint.checkpoint(layer, x, use_reentrant=False)`
